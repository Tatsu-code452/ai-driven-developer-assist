# Git運用標準

> 文書状態: 承認済み（2026-11-05）。

## 1. 目的・適用範囲

本書は、GitとGitHubを使う本プロジェクトの変更作業を、タスク単位で分離し、追跡可能にするための標準を定める。

## 2. 確認済みの前提

- バージョン管理にはGit、リポジトリ管理にはGitHubを利用する。
- AIの作業単位ごとにブランチを利用し、1作業1ブランチを基本とする。
- 成果物本文にバージョン情報を重複して保持せず、Gitの履歴を使う。
- 現在の既定ブランチは`main`である。既定ブランチの変更時は本書も見直す。

## 3. 運用標準

### 3.1 作業分離

- 1チケットにつき1ブランチ・1ワークツリーを使い、別チケットの変更を混在させない。
- `main`上で直接編集しない。作業ブランチを作成し、作業開始時にブランチ名・リポジトリルート・作業ツリーの状態を確認する。
- ブランチ名は`task/TSK-xxx`とする。チケットIDがない作業は`task/NO-TICKET-<短い-kebab-case説明>`とする。
- 作業範囲に必要なファイルのみ変更し、既存の未コミット変更を上書き・破棄しない。

### 3.2 変更・統合

- 変更前に対象ブランチと作業ツリーの状態を確認する。完了時は差分を確認し、無関係なファイルや秘密情報が含まれていないことを確認する。
- 変更に対応したテスト・ビルド・Lintを実行し、独立レビューを受けてから統合を判断する。未実施の確認を成功として報告しない。
- `reset --hard`、`clean -fd`、強制push、履歴書き換えなど、作業喪失や共有履歴変更につながる操作を行わない。
- commit、push、merge、releaseは、依頼と権限が明示された場合に限って実行する。レビュー・検証ゲートを満たす前に統合しない。

### 3.3 コミット・Pull Request

- 変更内容と検証結果を説明できる単位で記録し、生成物や秘密情報を混ぜない。
- コミットメッセージは`type(scope): summary`形式とする。Pull Requestには目的、変更範囲、関連チケット、検証結果、未解決事項を記載する。
- `main`へのPull Requestは作成者以外の1名以上による承認と、必須CIステータスチェックの成功後にマージする。これらの条件はGitHubの保護ブランチ設定に反映する。
- マージ方式はSquash Mergeとする。
