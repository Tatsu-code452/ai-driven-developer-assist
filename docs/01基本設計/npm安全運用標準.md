# npm安全運用標準

> 文書状態: 依頼者回答反映・承認済み（2026-11-05）。

## 1. 目的・適用範囲

本書は、npm依存関係とインストール処理を再現可能かつ安全に管理するための標準案を定める。対象はリポジトリ内のnpmプロジェクトと、開発・CIでのnpm利用とする。

## 2. 確認済みの前提

- リポジトリにはルート、`frontend/`、`backend/`、`app/`の各`package.json`と対応する`package-lock.json`がある。
- 開発環境構築手順書はNode.js LTS、`npm audit`、CIでの`npm ci`、初回の`npm install --ignore-scripts`を記載している。
- パッケージ間で依存バージョンの指定方法は統一されていない。Node.js/npmの固定バージョンと脆弱性のCIブロック基準は本書の運用ルールに従う。

## 3. 運用標準案

### 3.1 依存関係の追加・更新

- 依存追加は必要な機能に限定し、追加前にパッケージの用途、保守状況、ライセンス、依存関係、install lifecycle scriptの有無を確認する。
- `package.json`を変更した場合は該当プロジェクトの`package-lock.json`も更新し、両方を差分レビュー対象にする。依存変更のない作業でlockfileを再生成しない。
- 新規依存のバージョン指定は、特段の互換性・安全性上の理由がなければ`^`範囲指定とし、理由がある場合は完全固定を選択できる。lockfileを必ずコミットし、既存依存の指定方式は一括変更しない。

### 3.2 インストール

- CIやロックファイルに基づく再現可能な環境構築では、対象npmプロジェクトのルートで`npm ci`を使う。`package-lock.json`がない、またはマニフェストとlockfileが不整合の場合は、原因を確認して修正し、`npm install`でCIの差異を隠さない。
- install scriptを必要としない初回導入では、環境構築手順に従い`npm install --ignore-scripts`を使う。依存がscriptを必要とする場合は、その内容・必要性を確認してから許可する。機械的にscriptを無効化して、インストール成功を装わない。
- package managerを混在させず、npmプロジェクトではnpmと`package-lock.json`を使う。

### 3.3 脆弱性・秘密情報

- 依存変更後に`npm audit`を実行し、結果と対応方針を記録する。監査結果を確認せずに「安全」と判断しない。
- `npm audit fix --force`や大規模な依存更新を自動適用しない。破壊的更新を含む変更は影響とテストを確認し、個別にレビューする。
- 脆弱性監査は依存変更ごとに実行し、CIでは週次にも実行する。CriticalまたはHighの脆弱性が検出された場合はCIを失敗させ、直ちにトリアージする。MediumおよびLowは影響と修正版の有無を評価して対応タスクを記録する。Critical/Highの例外は原則認めず、やむを得ない場合は理由、緩和策、期限（最長30日）を記録し、プロジェクト責任者の承認を得る。
- トークン、パスワード、秘密鍵をソース、`package.json`、lockfile、ログへ記録しない。環境設定や認証情報をコミットしない。
- Node.jsはActive LTSを使用し、利用する正確なパッチバージョンを`.nvmrc`およびCIで固定する。Node.jsに同梱されるnpmを使用し、ローカルとCIでNode.js/npmのバージョンを一致させる。セキュリティ更新を毎月確認し、新しいLTSは提供開始後30日以内に採用可否を評価する。

## 4. 未決事項への回答（依頼者承認済み）

- Node.jsおよびnpmの固定方法と更新時期。⇒ Active LTSのNode.jsパッチバージョンを`.nvmrc`およびCIで固定し、同梱npmを使用する。セキュリティ更新を毎月確認し、新LTSは30日以内に評価する。
- 脆弱性監査のCI実行頻度、失敗閾値、例外承認者。⇒ 依存変更ごとおよびCI週次で監査し、Critical/Highで失敗させる。例外は理由・緩和策・最長30日の期限を記録し、プロジェクト責任者の承認を要する。
- 新規依存に対するバージョン指定方式の統一。⇒ 原則`^`範囲指定とlockfileを用い、互換性・安全性上の理由がある場合のみ完全固定を選択する。既存指定は一括変更しない。
