# コーディング規約

> 文書状態: 依頼者回答反映・承認済み（2026-11-05）。適用済みの規約と、既存コードへの移行を伴う事項を区別する。

## 1. 目的・適用範囲

本書は、本プロジェクトのソースコードを作成・変更するときの共通基準を定める。対象は、現在のリポジトリにあるReact／TypeScriptの画面、Node.js／TypeScriptのバックエンド、および関連スクリプトとする。

## 2. 確認済みの前提

- 技術スタック設計はReact、TypeScript、Node.js、Expressを採用対象としている。
- リポジトリには`frontend/`、`app/`、`backend/`のnpmプロジェクトがある。
- `frontend/`と`app/`にはESLint設定とTypeScriptビルドがあり、`backend/`にはTypeScriptビルドとVitestテストがある。
- React画面は`PascalCase`のコンポーネント名・ページファイル、バックエンドのコントローラーやサービスは`camelCase`のファイル名を使う例がある。既存の命名は一律ではない。

## 3. 規約

### 3.1 型・境界

- TypeScriptを使う領域では、型を明示してデータの形を保つ。型情報を安易に無効化する`any`や型アサーションに頼らず、必要な場合は入力検証・型ガードで安全性を確保する。
- HTTP、ファイル、環境変数など、信頼できない境界から受け取る値は利用前に検証する。
- 公開APIや複数モジュールから利用する関数・データ型は、意図が読み取れる型を定義する。

### 3.2 命名・ファイル

- 関数・変数は`camelCase`、型・クラス・Reactコンポーネントは`PascalCase`を基本とする。モジュール定数は`UPPER_SNAKE_CASE`、ローカル定数は`camelCase`とする。
- Reactコンポーネントは`.tsx`、TypeScriptの非UIモジュールは`.ts`を使う。
- 新しいファイルは対象レイヤーの既存パターンに合わせる。新規バックエンドのモジュールファイル名は`camelCase`とする。既存ファイルの一括改名は行わない。

### 3.3 構成・エラー処理

- 画面、API呼び出し、ドメイン処理を責務に応じて分け、既存の`pages`、`services`、`controllers`、`repositories`等の構成を尊重する。
- エラーを握りつぶしたり、成功したように見える既定値へ置き換えたりしない。利用者に伝えるエラーは既存の画面・APIエラー処理へ接続する。
- コメントは、コードだけでは判断しにくい制約や理由を説明する場合に限る。

### 3.4 React・アクセシビリティ

- 既存のReact Router、サービス層、フックの使い方を優先する。
- 入力・操作要素はラベルと目的が判別できるようにし、読み込み中・エラー・空の状態を適切に区別する。
- Hooksの規則に従い、画面コンポーネントに無関係な通信・変換処理を重複して埋め込まない。

### 3.5 品質確認・テスト

- 変更したnpmプロジェクトに定義済みのESLint、ビルド、テストを実行し、失敗・未実施を報告する。
- 振る舞いを追加・変更した場合は、既存のVitestパターンに沿って対象ロジックのテストを追加または更新する。テストスクリプトのないパッケージにテスト実行済みとは記載しない。
- Prettierを共通フォーマッターとし、新規・変更ファイルに適用する。既存ファイルを一括整形しない。パッケージに設定やスクリプトが未導入の場合は、未実施として明記し、ツール導入を別途扱う。
- 品質確認は、変更対象パッケージに定義されたLint、型検査またはビルド、テスト、および設定済みの場合のPrettierチェックで行う。該当するスクリプトやツールがない場合は、その旨を記録し、成功扱いにしない。
- 1ソース200行は分割を検討する目安とし、超過だけを理由に分割を強制しない。単一の責務としてまとまる場合は理由を確認して維持できる。
- 関数式・アロー関数は既存の使用箇所やコールバックで優先する。名前付き関数宣言はトップレベルの処理を明確にする場合に使用できる。classは状態・不変条件・依存性のまとまりを表す場合に使用できる。オブジェクトの契約には`interface`を優先し、共用体等には`type`を使う。

## 4. 未決事項への回答（依頼者承認済み）

- 全パッケージ共通のフォーマッターと整形ルール。⇒ Prettierを共通フォーマッターとし、新規・変更ファイルに適用する。既存ファイルは一括整形しない。
- 定数名および新規バックエンドファイルの命名統一。⇒ モジュール定数は`UPPER_SNAKE_CASE`、ローカル定数は`camelCase`、新規バックエンドのモジュールファイル名は`camelCase`とする。
- REQ-039の「品質が統一されたソース作成」を測定する尺度。⇒ 変更対象パッケージで定義済みのLint、型検査またはビルド、テスト、設定済みのPrettierチェックを実施し、未実施や失敗を記録する。
- 関数宣言、class、関数式、アロー関数、interfaceの使い分け。⇒ 関数式・アロー関数を既存パターンやコールバックで優先し、トップレベルの明瞭さには名前付き関数宣言、状態や不変条件の表現にはclass、オブジェクト契約には`interface`を使う。
- 1ソース200行を目安とする規則。⇒ 200行は分割検討の目安とし、超過のみを理由に分割しない。単一責務としてまとまる場合は維持できる。
